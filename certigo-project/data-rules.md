# Данные CertiGo

Комплект работает с зафиксированным срезом данных в PostgreSQL 16. Локальная база `certigo` создаётся из `schema.sql` и `seed.sql`.

## Граница набора

* Период наблюдения: с `2026-03-09 00:00:00+03` по `2026-05-31 23:59:59+03` (12 недель, W1–W12).
* Период A/B-эксперимента `onboarding_v2`: с `2026-05-04 00:00:00+03` по `2026-05-31 23:59:59+03` (недели W9–W12).
* Все временные метки — `timestamptz`, в наборе зафиксирован часовой пояс `Europe/Moscow`.
* После выполнения `schema.sql` и `seed.sql` разрешены только читающие запросы (`SELECT`, читающие `WITH`).

## Детализация таблиц

| Таблица | Одна строка | Основной идентификатор |
|---|---|---|
| `channels` | один канал привлечения | `channel_id` |
| `users` | один зарегистрированный пользователь | `user_id` |
| `ab_assignments` | назначение одного пользователя в один вариант одного эксперимента | `assignment_id`; уникальность по `(user_id, experiment_name)` |
| `events` | одно продуктовое событие пользователя | `event_id` |
| `payments` | одна попытка оплаты пользователя | `payment_id` |
| `marketing_spend` | расходы одного канала за один месяц | `spend_id` |

## Каналы, платформы, тарифы

* Каналов три: `search_ads`, `social_ads`, `organic`. Расходы есть только у платных каналов (`search_ads`, `social_ads`); у `organic` строк в `marketing_spend` нет — это свойство канала, а не ошибка загрузки.
* `users.platform`: `ios`, `android`, `web`. Для основных вопросов проекта платформа не нужна, но поле может пригодиться для дополнительных срезов.
* Тарифа два: `monthly` (2 990 ₽) и `annual` (9 990 ₽). Средний чек и ARPU считаются по фактическим суммам `amount_rub`, а не подстановкой одной цены.

## События и воронка

* Словарь `events.event_name`: `registration`, `onboarding_started`, `onboarding_completed`, `trial_started`, `paywall_viewed`. Других значений нет.
* Воронка проекта: `registration` → `onboarding_completed` → `trial_started` → `paywall_viewed` → успешная оплата. Оплата хранится не в `events`, а в `payments`.
* Единица счёта на каждом этапе воронки — уникальный пользователь (`COUNT(DISTINCT user_id)`), а не количество строк событий.
* Этап `onboarding_started` в основную воронку не входит; он нужен для диагностики, где именно теряются пользователи.
* Конверсия этапа делится на количество пользователей предыдущего этапа воронки. Общая конверсия `cr_total` делится на `registration`.

## A/B-эксперименты

* В `ab_assignments` два эксперимента. К вопросу руководителя относится только `onboarding_v2`. Эксперимент `paywall_copy_v3` проводился раньше (апрель), уже завершён и в анализ не входит — фильтруйте `experiment_name` явно.
* В `onboarding_v2` участвуют только пользователи, зарегистрированные с `2026-05-04 00:00:00+03` и позже. У остальных пользователей строки с этим экспериментом нет; при соединении с `users` это даёт `NULL` — ожидаемое состояние, а не ошибка. Включать таких пользователей в сравнение вариантов нельзя.
* Основная метрика: доля `onboarding_completed` среди назначенных в вариант.
* Guardrail-метрика: доля успешных оплат (`payments.status = 'succeeded'`) среди назначенных в вариант.
* Правило решения — в `ab-brief.md`.

## Платежи и выручка

* `payments.status`: `succeeded`, `refunded`, `failed`. Выручкой считаются только `succeeded`. Возвраты и неуспешные попытки в выручку, ARPU и ROMI не входят — это контролируемая ловушка набора.
* У одного пользователя в наборе не более одного платежа, но при соединении `users` с `events` строки размножаются: у пользователя несколько событий. Для подсчёта пользователей после такого соединения нужен `COUNT(DISTINCT user_id)`.

## Юнит-экономика по каналам

* Считается только по платным каналам (`search_ads`, `social_ads`): у `organic` нет расходов, и CAC для него не определён.
* Период расчёта: весь период наблюдения W1–W12.
* `spend_rub` канала — сумма `marketing_spend.spend_rub` по всем трём месяцам (`2026-03`, `2026-04`, `2026-05`).
* `CAC = spend_rub / новые пользователи канала`.
* `ARPU = выручка succeeded пользователей канала / новые пользователи канала`.
* `ROMI = выручка succeeded / spend_rub`.
* Канал считается экономически приемлемым при `ARPU >= CAC` (эквивалентно `ROMI >= 1`).
* Знаменатель CAC и ARPU — все новые пользователи канала за период, включая не оплативших.

## Проверка загрузки и результатов

`CONTROL.md` содержит только шесть количеств строк для проверки корректной загрузки базы. После подготовки файлов в `submission/` запускайте `node check.mjs`.

Если SQL-запрос или экспорт не проходит проверку, вернитесь к определениям в этом файле, схеме и фактически полученному результату запроса. Не подставляйте числа вручную.
